# Обязательный цикл проверки connector

Владелец решения: maintainer TGSUM. Текущий review: 2026-09-26.
Проверять отдельно каждый `(platform, acquisition_method)` из
[registry.json](registry.json). Поля описаны [JSON Schema](registry.schema.json).

## Когда запускать

- Перед новой интеграцией, изменением API/SDK, формата архива, авторизации,
  полномочий, retention, автоматизации клиента или AI-передачи.
- Перед выпуском затронутого connector и при изменении platform terms,
  API version, quotas, app-review/distribution rules или поддерживаемой ОС/клиента.
- Плановый пересмотр: каждые **30 дней** для network/client automation,
  **90 дней** для file/local import. Это наша политика, не требование платформ.
  `next_review_due_at` фиксирует следующую дату; календарное время не является
  подтверждением, что проверка выполнена.

## Цикл и результат каждого шага

| Шаг | Требуемый результат |
| --- | --- |
| 1. Scope | Beads issue: use case, account/tenant type, ОС, способ acquisition, выбранные чаты, планируемый retention и AI destination |
| 2. Первичные источники | URL + дата + версия API/клиента/commit; отдельно факт, вывод и неизвестное; недоступный источник помечен, не заменён предположением |
| 3. Access/policy | Методы и pagination, реальный token grant, выдача scopes/admin consent, distribution, quotas, storage/deletion, AI inference/cloud/training; конкретные условия и основания |
| 4. Контрактный spike | Разрешённые fixtures или тестовый аккаунт; identity, порядок/границы, edits/deletes, attachments, retry/expiry/revoke, длинный offline gap и completion |
| 5. Support decision | Обновлённый registry: supported/candidate/research/excluded/deferred, enabled operations и ограничения; причина + незакрытые вопросы |
| 6. Реализация | Минимальный адаптер с regression fixtures и проверкой совместимости; незаявленные возможности отключены |
| 7. Перед выпуском | Проверка актуальности первичных источников, evidence реализации и UI-текста; запись решения/версии и следующего срока в Beads |

Шаги 2–3 выполняются до использования рабочего аккаунта. Spike с синтетическими
данными может закрыть техническую гипотезу; он не доказывает разрешение AI-use
для реальных рабочих чатов. Нужное разрешение владельца аккаунта или платформы
получают для конкретного действия, если оно ещё не предоставлено.

## Что обязательно различать

- Capability API, реализованную capability TGSUM и полноту конкретного snapshot.
- `selected_scope` и `authorization_scope`; где именно применяется ограничение.
- Import существующего файла и acquisition через авторизованный клиент.
- Локальное inference, передачу облачному inference и обучение/fine-tuning.
- Соблюдение API rules, согласие участников и политику организации/получателя.
- Technical failure, неизвестный пункт правил и подтверждённое ограничение.

Наличие метода или отсутствие найденного запрета не заполняет `ai_policy`
значением allowed. Checkbox пользователя не заменяет согласия иных лиц или
разрешение платформы, если они требуются. При неопределённости записывать
конкретный вопрос и держать соответствующую операцию выключенной.

## Изменение статуса и устаревание

`candidate` — перспективный способ; `research` — существенные открытые вопросы;
`excluded` — несовместим с выбранным use case; `deferred` — не в текущей очереди.
`supported` требует проверенной реализации; сейчас это только существующий
Telegram full-export import. Ни один новый network/AI путь этим registry не включён.

Дата `last_policy_reviewed_at` означает чтение перечисленных источников,
не юридическое одобрение. `review_level: initial` оставляет открытые вопросы.
При недоступном источнике не обновлять дату успешной проверки без пометки причины.

Просроченный review, существенное изменение условий или новый blocker останавливают
выпуск/расширение затронутой capability до повторной проверки. Существующие
пользовательские файлы не удаляются из-за истечения даты. Отзыв доступа, прекращение
сбора и требование удаления данных рассматриваются отдельно по конкретной policy.

## Где действует gate сейчас

Обязательный порядок закреплён в корневом `AGENTS.md`; реестр — машиночитаемый
артефакт проектирования. В текущем приложении ещё нет runtime loader, remote kill
switch, планировщика policy checks или CI job, автоматически проверяющего сроки.
Поэтому нельзя говорить, что изменение JSON уже отключает работающий connector.

Перед первым live выпуском реализовать loader и release check: уникальные ID,
валидная schema, источники, свежесть, доказательства support promotion и запрет
включения нерешённых network/AI capabilities. Remote updates, если понадобятся,
должны быть отдельной явной функцией с проверкой подлинности; offline import
не должен скрыто обращаться в сеть за registry.

## Запись в Beads

Хранить outcome, ссылки на исследование/fixtures, revision проверенного кода,
решение, открытые вопросы и следующий шаг. При повторном review обновлять запись
и registry вместе. API secrets, сессии, реальные сообщения и personal fixtures
в публичные docs/Beads remote не сохранять.
