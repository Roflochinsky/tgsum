# Обязательный цикл проверки connector

Владелец решения: maintainer TGSUM. Процесс обновлён: 2026-09-27.
Проверять отдельно каждый `(platform, acquisition_method)` из
[registry.json](registry.json). Поля описаны [JSON Schema](registry.schema.json).
Для записи исследования использовать [шаблон review](review-template.md).

Это внутренний процесс выбора и выпуска интеграций. По
[продуктовому принципу](../adr/0002-user-controlled-content.md) пользователь
решает вопросы использования содержимого; TGSUM не проверяет согласие каждого
участника и не превращает research-поля registry в юридический gate для Run.

## Когда запускать

- Перед новой интеграцией, изменением API/SDK, формата архива, авторизации,
  полномочий, retention, автоматизации клиента или AI-передачи.
- Перед выпуском затронутого connector и при изменении platform terms,
  API version, quotas, app-review/distribution rules или поддерживаемой ОС/клиента.
- Плановый пересмотр: каждые **30 дней** для network/client automation,
  **90 дней** для file/local import. Это наша политика, не требование платформ.
  `next_review_due_at` фиксирует следующую дату; календарное время не является
  подтверждением, что проверка выполнена.

## Цикл и результат каждого шага

| Шаг | Требуемый результат |
| --- | --- |
| 1. Scope | Beads issue: use case, account/tenant type, ОС, способ acquisition, выбранные чаты, планируемый retention и AI destination |
| 2. Первичные источники | URL + дата + версия API/клиента/commit; отдельно факт, вывод и неизвестное; недоступный источник помечен, не заменён предположением |
| 3. Access/policy | Методы и pagination, реальный token grant, выдача scopes/admin consent, distribution, quotas, storage/deletion и ограничения платформы на интеграцию/AI; вывод для архитектуры и выпуска |
| 4. Контрактный spike | Разрешённые fixtures или тестовый аккаунт; identity, порядок/границы, edits/deletes, attachments, retry/expiry/revoke, длинный offline gap и completion |
| 5. Support decision | Обновлённый registry: supported/candidate/research/excluded/deferred, enabled operations и ограничения; причина + незакрытые вопросы |
| 6. Реализация | Минимальный адаптер с regression fixtures и проверкой совместимости; незаявленные возможности отключены |
| 7. Перед выпуском | Проверка актуальности источников, evidence реализации и точности технических обещаний UI; запись решения/версии и следующего срока в Beads |

Шаги 2–3 выполняются до реализации нового способа подключения. Для spike
использовать предоставленные fixtures/тестовый аккаунт; вход и действия от имени
пользователя требуют его авторизации, если она ещё не дана. Результат spike
закрывает техническую гипотезу; право пользователя анализировать рабочие данные
приложение не устанавливает.

## Что обязательно различать

- Capability API, реализованную capability TGSUM и полноту конкретного snapshot.
- `selected_scope` и `authorization_scope`; где именно применяется ограничение.
- Import существующего файла и acquisition через авторизованный клиент.
- Локальное inference, передачу облачному inference и обучение/fine-tuning.
- Обязанности разработчика интеграции и решения пользователя/его организации.
- Technical failure, неизвестный пункт правил и подтверждённое ограничение.

Наличие метода или отсутствие найденного запрета не заполняет `ai_policy`
значением allowed. Неизвестный пункт фиксируется как исследовательский вопрос
для maintainer; поддержку конкретной интеграции определяют по техническим
доказательствам и применимым условиям. Поле `ai_policy` не вычисляет права
конкретного пользователя и не блокирует анализ его локального файла автоматически.

## Изменение статуса и устаревание

`candidate` — перспективный способ; `research` — существенные открытые вопросы;
`excluded` — несовместим с выбранным use case; `deferred` — не в текущей очереди.
`supported` требует проверенной реализации; в текущих исходниках это Telegram
full-export и single-chat JSON import с синтетическими regression fixtures.
Project/snapshot/diff и assisted export не доказывают автоматическую выгрузку
официальным клиентом. Новые network/AI пути этим registry не включаются.

Дата `last_policy_reviewed_at` означает чтение перечисленных источников,
не юридическое одобрение. `review_level: initial` оставляет открытые вопросы.
При недоступном обязательном источнике записать неудачную попытку и причину в
исследование/Beads; сохранить прежние дату успешной проверки и её deadline.

Просроченный review, существенное изменение условий или новый blocker требуют
повторной проверки перед выпуском/расширением затронутой capability. Дата review
не отключает локальный анализ и не удаляет пользовательские файлы. Отзыв API
доступа останавливает acquisition; явное удаление и retention-настройки пользователя
управляют локальными данными.

## Где действует gate сейчас

Обязательный порядок закреплён в корневом `AGENTS.md`. Schema 2, offline CLI,
CI/release gate и библиотечный technical loader реализованы в
[контракте registry](../development/connector-registry.md). Проверка выпуска
проверяет уникальность IDs, schema, owner/dates, evidence paths, implementation
revision и квалификацию, а также свежесть review включённых профилей. При обычной
разработке просрочка даёт напоминание; перед выпуском включённого профиля — ошибку.

Runtime получает реализованные возможности из зарегистрированного кода,
проверяет известный format/client version и отдельно сообщает scope квалификации.
Coverage остаётся фактом конкретного snapshot. `ai_policy` не разрешает/запрещает
Run. Изменение JSON не выключает существующий локальный импорт и не удаляет данные.
Remote kill switch и автоматическое обновление дат не реализованы. Отдельный
UI статуса — отдельный срез `2ty.2`.

## Напоминания о сроках

Локально и в CI используется один offline validator:

```sh
cargo run --locked -p tgsum-core --bin connector-registry -- --reminders --within-days 14 > /tmp/connector-review.json
python scripts/connector-review-summary.py /tmp/connector-review.json
```

Отчёт включает overdue, unknown и upcoming review; deadline в точности через
14 дней входит в выборку. Даты считаются по UTC. `--today YYYY-MM-DD` позволяет
воспроизвести отчёт; `--within-days 0` показывает только due/unknown.
У каждой строки есть owner, успешная дата, deadline, evidence, primary URLs
и признак реализации из кода. Unknown не исчезает из списка из-за будущего deadline.
Никаких запросов к источникам, изменений registry или создания GitHub Issues нет.

CI `connectors` сохраняет JSON и Markdown summary на каждом обычном прогоне.
Workflow `Connector review reminders` задаёт еженедельную проверку в понедельник
08:17 UTC с горизонтом 14 дней. GitHub запускает schedule только с default branch;
пока изменения находятся на рабочей ветке, этот schedule ещё не активен. Возможны
задержки GitHub и отключение schedule при длительном отсутствии активности, поэтому
release-check независимо проверяет актуальную дату на каждом выпуске.
[GitHub schedule, проверено 2026-09-27](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Reminder не является успешным research. Maintainer читает первичные источники,
заполняет шаблон, фиксирует решение и только затем обновляет даты/evidence.
Перед выпуском `--release` сохраняет прежнее строгое поведение, включая ошибку
для просроченной реализации. Обычная просрочка в reminder-режиме — work item,
не запрет на локальную обработку данных.

## Запись в Beads

Хранить outcome, ссылки на исследование/fixtures, revision проверенного кода,
решение, открытые вопросы и следующий шаг. При повторном review обновлять запись
и registry вместе. API secrets, сессии, реальные сообщения и personal fixtures
в публичные docs/Beads remote не сохранять.
