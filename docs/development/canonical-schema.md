# Canonical snapshot schema 2

Implemented in `tgsum-hzm.2` on 2026-09-26, on top of the Telegram foundation.
This describes the development branch, not a new release or a live connector.

## Identity, revisions and provenance

Native IDs remain strings in the platform/account/conversation/message key.
Each record now carries identity quality, deletion state, normalized timestamp
certainty and provenance: snapshot ID, zero-based ordinal within the selected
conversation's messages, locator kind and optional raw-record digest.

`revision_id` is SHA-256 of a versioned canonical content projection. The
projection includes identity, raw timestamps, sender, text, reply/thread,
service fields, attachment references and deletion state. It excludes import
time, snapshot ID and record order. The snapshot content digest includes the
source, conversation title/kind and sorted message keys/revisions. Thus a
re-export or reordered archive preserves message revisions; content edits
change them. These hashes detect accidental inconsistency, not a malicious
local rewrite. They are private data, not anonymous public evidence IDs.

`Snapshot::diff` compares content revisions. Observation changes alone do not
count as edits. A missing record remains `missing`, even with claimed complete
coverage. Telegram records are `present`; this importer has no evidence of
deletion. Other adapters can supply explicit `deleted` tombstones through the
[common observation contract](connectors.md); diff reports those separately.
No Telegram archive disappearance generates an explicit deletion event.

Attachment metadata now has optional native identity and content digest. They
remain absent for Telegram JSON references: file bytes have not been read.
Likewise, the message raw digest stays absent. The canonical content hash is
not represented as a hash of the original archive or of an attachment.

## Time and coverage

Raw exported timestamp strings are retained. A valid decimal Unix time yields
an explicit UTC instant; an RFC 3339 offset can do the same. Fractional seconds
are retained as nanoseconds. A local date without either remains
`unknown_timezone`; host timezone settings are never used. Missing, invalid
and conflicting values have separate statuses. If two explicit time sources
disagree by epoch second, UTC remains unknown. Leap seconds are not normalized.

Snapshot `imported_at` means local import time, not client acquisition time.
`coverage.range` is an optional inclusive UTC range claimed by a connector;
it is never inferred from the first/last observed message. Known gaps retain
their range (if known) and reason. `complete` requires a range, nonempty evidence
and no known gaps. This validates claim structure, not the external truth of
the evidence. Telegram JSON still imports as `unknown` with no claimed range.

## Compatibility

`SnapshotStore::load` upgrades schema 1 in memory and leaves original bytes
unchanged. It reconstructs content revisions and time certainty from retained
fields. It records `migrated_from_schema: 1`, a canonical-record locator and no
import time; source-record bytes and acquisition history cannot be recovered.
The committed synthetic `snapshot-v1.json` fixture was generated by schema 1
before this change and is read by the migration test.

Unknown versions, inconsistent provenance, modified content without matching
revisions and unsupported complete-coverage claims are rejected. Newly imported
snapshots use schema 2. Returning to an older application does not downgrade
new snapshots; preserve a compatible binary and the immutable original data.

The additional metadata increases storage and validation work; previous schema
1 performance numbers in `archive-core.md` do not measure schema 2. Parsing
still holds one chat; snapshot comparison holds two selected snapshots.
