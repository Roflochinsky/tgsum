# Автоматический анализ импортированных чатов: core

Срез `tgsum-506.11.1`, 2026-09-28. Реализация: `core/src/automation.rs`,
`core/src/automation/storage.rs`; сценарии: `core/tests/automation.rs`.

Это библиотечный движок одного задания на Project. Он анализирует **уже
импортированные snapshots**. Desktop пока не регистрирует executor, не вызывает
этот движок по таймеру и не показывает настройку задания. Автоматическую выгрузку
Telegram обеспечивает отдельный [bridge](bridge-schedule.md), чей настоящий
OS driver ещё не квалифицирован. Импорт файла сам по себе не включает анализ.

## Контракт

| API `ProjectStore` | Поведение |
| --- | --- |
| `automation` | Последняя сохранённая настройка и состояние |
| `configure_automation` | Проверяет показанную ревизию Project и задания; связывает selected scope, privacy, recipe, модель и получателя; сохраняет на паузе |
| `pause_automation` | Явно включает/приостанавливает; проверяет ревизию, scope и expiry, сохраняет историю попыток |
| `tick_automation` | Одна проверка срока с переданными часами, executor и отменой; готовит bundle, проверяет результат и сохраняет analysis/baselines |
| `acknowledge_automation_interruption` | После проверки host, что старый процесс остановлен, помечает прерванное задание и оставляет на паузе; inference не повторяет |

`AutomationSettings` содержит cadence, `AnalysisSpec`, expiry и предел context
bytes. Интервалы — шесть часов или сутки **от последней попытки**, не календарное
«каждое утро в 09:00». Первый tick после включения может выполниться сразу.
Пропущенные интервалы не образуют очередь. Настройка действует до указанного
срока, максимум 30 суток от её сохранения. Обратный ход часов не ускоряет запуск.
Новый grant нужен после expiry или изменения выбранных источников/фильтров,
имени Project, privacy/custom terms, лимита нарезки либо версии sanitizer.
Повторный импорт того же source не меняет grant.

Executor получает только `AnalysisSpec`, публичный `BundleManifest` и очищенные
документы context. Credentials, исходные пути, snapshot и private evidence index
в этот контракт не входят. Spec описывает исполнение, но не подтверждает наличие
или квалификацию агента. `available` проверяет host; `analyze` обязан сам соблюдать
deadline, cancellation и успешность process/transport перед возвратом результата.
Core не может принудительно остановить зависший callback.

## Один запуск

1. Межпроцессная блокировка исключает второй automation worker этого Project.
   Paused/expired/изменённый scope, незавершённый Telegram refresh, занятость,
   отсутствие executor или ранний срок не вызывают агента.
2. `Running` и время попытки сохраняются **до** подготовки и внешнего вызова.
3. Проверяются snapshots **всех** включённых sources. Отсутствующий источник
   останавливает весь запуск; ограниченная/неизвестная coverage передаётся как
   есть и не становится полной. Пустая выборка даёт `NoMessages` без анализа.
4. Создаётся bundle по сохранённой privacy policy. Неразрешённые находки,
   отсутствующие выбранные вложения и выбор вложений вне scope требуют review.
   Суммарный объём документов ограничен настройкой (1..=1 MiB); это ограничение
   входных bytes, не денежный или token budget.
5. SHA-256 очищенных документов и coverage сравнивается с последним успешным
   запуском. Неизменившийся контекст даёт `NoChanges` без inference. Новые ID
   snapshot/bundle сами по себе не вызывают повтор. Отдельного исторического
   кеша всех когда-либо виденных состояний нет.
6. Сохраняется обычный analysis request, повторно проверяются scope, expiry,
   cancellation и актуальность ticket. Executor возвращает типизированный output.
7. Recipe validator проверяет evidence ID/revision и структуру; результат и
   baselines публикуются через существующий [analysis lifecycle](analyses.md).
   Ошибки, отмена, истёкшая настройка или изменённый Project baseline не двигают.
   Ошибка/отмена ставит задание на паузу, автоматического retry нет.

В delta-режиме используются общие baselines Project. Ручной успешный анализ
тоже может их передвинуть. Независимые расписания/курсор каждого recipe и
объединение старых summaries этим срезом не реализованы.

## Хранение и прерывание

`projects/<id>/automation/<20-digit-revision>.json` — отдельные immutable записи
schema 1, максимум 128 KiB. Project schema не изменяется. Новый файл публикуется
через synced temporary file и no-clobber; `lease` содержит OS lock. Повреждённая
последняя запись не приводит к откату на прежнее включённое задание. Проверяются
identity/version, обычные файлы/каталоги; Unix directory mode 0700. Как и
[Project storage](projects.md), это не защита от параллельной подмены файлов
процессом того же пользователя и не обещание устойчивости к отключению питания.

Crash/panic оставляет `Running`: следующие ticks требуют разбора и не повторяют
агента. Это верно и при сбое между commit baseline и финальной записью состояния.
Сохранённый journal/result остаётся доступен для явного recovery. Acknowledge не
объявляет успех, не принимает результат и не запускает анализ; после него нужна
явная команда resume либо новая настройка. Пауза во время работающего callback
возвращает busy; немедленную остановку host передаёт через cancellation.

## Что подключить в desktop следующим срезом

- UI выбора scope/recipe/модели/получателя/интервала, review и отдельного opt-in;
  состояния последнего запуска, pause/resume/cancel и expiry.
- Host timer с обработкой sleep/restart и доступности локального контекста.
- Общий execution gate с ручным анализом, привязка проверенного executable,
  версии, профиля изоляции и выбранной авторизации. Lock core исключает только
  automation workers одного Project; он не блокирует ручной Run/другой Project.
- Adapter к существующим runners с ограничением длительности и выходных данных.
  В production этот core API пока не вызывает ни Codex, ни Claude.
- Связь с успешным acquisition перед анализом и явное отображение давности
  snapshot. Проверка реального клиента/аккаунта остаётся под контролем пользователя.

## Evidence и граница review

Используются существующие контракты [bundles](bundles.md),
[recipes](recipes.md), [privacy](privacy-controls.md) и
[ручного desktop Run](desktop-analysis.md). API/формат Telegram, auth и способ
передачи провайдеру не меняются: новый executor проверен только локальной
подставной реализацией. Этот срез не квалифицирует scheduled cloud execution;
его review обязателен перед регистрацией настоящего runner. Registry сохраняет
текущие support/operations и даты platform review.

Проверки воспроизводимы без аккаунтов:

```sh
cargo test --locked -p tgsum-core --test automation
```

Сценарии покрывают расписание/expiry/паузы, несколько выбранных чатов и исключение
остальных, повторные импорты, delta без новых сообщений, пропавший второй source,
privacy/budget, forged evidence, ошибку/cancel/смену scope, crash/restart и конфликт
двух независимых процессов. Подставной executor не доказывает качество summary.
