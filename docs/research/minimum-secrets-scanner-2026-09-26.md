# Минимальный локальный secrets scanner

Проверено **2026-09-26** по публичным первичным источникам для `tgsum-hzm.5`.
Область: распознаваемые текстовые формы секретов перед подготовкой AI-контекста.
Проверка включала чтение документации и исходников; запросов с токенами,
проверок аккаунтов, получения ключей и вызовов messenger API не было.

Ниже отдельно приведены наблюдаемые факты и предлагаемые правила TGSUM.
Документ не подтверждает выпуск правил: фактическое покрытие определяют код
и синтетические regression fixtures. `High` означает достаточное основание
скрыть текст по локальной политике, а не доказательство активности секрета.

## Наблюдаемые форматы

### GitHub

GitHub документирует префиксы `ghp_` для classic PAT, `github_pat_` для
fine-grained PAT, `gho_` для OAuth, `ghu_` для user access token GitHub App,
`ghs_` для installation token и `ghr_` для refresh token.
[GitHub Docs, прочитано 2026-09-26](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#githubs-token-formats).

С 2026-04-27 началось поэтапное введение `ghs_APPID_JWT`. GitHub отдельно
предупреждает, что ожидание ровно 40 символов несовместимо с новым форматом.
Changelog от 2026-05-15, с правкой regex от 2026-05-26, рекомендует
`ghs_[A-Za-z0-9\.\-_]{36,}`; новый вариант содержит две точки и имеет длину
около 520 символов. Провайдер советует считать значение непрозрачной строкой.
[GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#githubs-token-formats),
[GitHub Changelog](https://github.blog/changelog/2026-05-15-github-app-installation-tokens-per-request-override-header/).

Старые непрефиксные 40-символьные hex-токены внешне похожи на хеши. Публикация
2021 года описывает Base62 и checksum для тогдашних новых токенов; это
историческое описание, не универсальная гарантия длины для всех типов 2026 года.
[GitHub Engineering, 2021-04-05, обновлено 2023-05-10](https://github.blog/engineering/behind-githubs-new-authentication-token-formats/).

### HTTP Authorization

Bearer credentials состоят из имени схемы, одного или нескольких пробелов
и непустого значения из ASCII букв, цифр, `- . _ ~ + /`, после которого
допустимы `=`. Bearer не обязан быть JWT или декодируемым Base64.
Обладание токеном является основанием доступа в описанной схеме.
[RFC 6750, 2012-10, §§1.2, 2.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1).

Basic передаёт Base64 от байтов `user:password`. Первое двоеточие отделяет
пользователя; дальнейшие относятся к паролю. Кодировка исходной строки по
умолчанию не обязана быть UTF-8. По форме Basic нельзя установить,
действительны ли учётные данные.
[RFC 7617, 2015-09, §2](https://www.rfc-editor.org/rfc/rfc7617.html#section-2).

Названия HTTP-полей и имена схем аутентификации регистронезависимы.
Общий `token68` допускает те же перечисленные символы и завершающие `=`.
[RFC 9110, 2022-06, §§5.1, 11.1–11.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.1).

### Приватные ключи

RFC 7468 задаёт границы `BEGIN`/`END` с пятью дефисами с каждой стороны,
регистрозависимой меткой и Base64-содержимым. Метки `PRIVATE KEY` и
`ENCRYPTED PRIVATE KEY` обозначают контейнеры PKCS #8. Отдельные метки
`PUBLIC KEY` и `CERTIFICATE` не означают приватный ключ.
[RFC 7468, 2015-04, §§2, 10–13](https://www.rfc-editor.org/rfc/rfc7468.html#section-10).

Исходник OpenSSH определяет границы `OPENSSH PRIVATE KEY`.
[OpenSSH Portable, tag `V_9_9_P2`, `sshkey.c`](https://github.com/openssh/openssh-portable/blob/V_9_9_P2/sshkey.c#L67).
OpenSSL определяет метки `RSA PRIVATE KEY`, `DSA PRIVATE KEY` и
`EC PRIVATE KEY`, дополнительно к контейнерам PKCS #8.
[OpenSSL, tag `openssl-3.5.0`, `include/openssl/pem.h`](https://github.com/openssl/openssl/blob/openssl-3.5.0/include/openssl/pem.h#L40).
Оба закреплённых исходника прочитаны 2026-09-26; это подтверждение конкретных
меток, а не утверждение о новейшей версии этих библиотек.

### URL с учётными данными

В RFC 3986 `authority` имеет вид `[userinfo "@"] host [":" port]` и
ограничивается следующим `/`, `?`, `#` либо концом URI. `userinfo` допускает
percent-encoding и двоеточия. Форма `user:password` устарела; RFC рекомендует
не показывать открытым текстом непустую часть после первого двоеточия.
Наличие такой строки не подтверждает способ авторизации конкретного сервиса.
[RFC 3986, 2005-01, §§3.2–3.2.1](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.2.1).

### JWT/JWE

JWT состоит из разделённых точками Base64url-частей; представление зависит
от JWS или JWE. JWT может содержать чувствительные сведения. Для доверия к
содержимому нужны проверки защиты и контекста; внешний вид их не заменяет.
`alg: none` допускает JWT с пустой подписью.
[RFC 7519, 2015-05, §§3, 6, 7.2, 11–12](https://www.rfc-editor.org/rfc/rfc7519.html).

Compact JWS содержит три сегмента, compact JWE — пять. JWS-контейнер может
нести произвольный payload, поэтому сам JWS-подобный вид ещё не доказывает JWT.
[RFC 7515, 2015-05, §§3.1, 3.3](https://www.rfc-editor.org/rfc/rfc7515.html#section-3.1),
[RFC 7516, 2015-05, §3.1](https://www.rfc-editor.org/rfc/rfc7516.html#section-3.1).

### Telegram: предел найденного подтверждения

Bot API показывает пример токена и путь `https://api.telegram.org/bot<token>/METHOD_NAME`.
В прочитанном разделе нет полной грамматики токена и гарантированных длин
числовой и секретной частей. Пример не обосновывает фиксированную standalone
regex для всех Telegram bot tokens.
[Telegram Bot API, прочитано 2026-09-26](https://core.telegram.org/bots/api#authorizing-your-bot).
Эта проверка не включает Telegram в минимальный набор самостоятельных правил.

## Предлагаемый набор правил TGSUM

Это проектные решения для локального scanner, не требования платформ и не
валидатор перечисленных протоколов. Правила применяются к декодированному
тексту входных полей; HTTP escaping, OCR и рекурсивное декодирование произвольных
строк сюда не входят.

| Правило | Действие по умолчанию | Границы и ограничения |
| --- | --- | --- |
| Известная метка приватного ключа | High, скрыть блок целиком | Закрывающая метка должна соответствовать открывающей. При незакрытом `BEGIN` скрыть остаток текущего поля и отметить неполный блок. Не ограничиваться удалением строк `BEGIN`/`END`. |
| Явное поле `Authorization` или `Proxy-Authorization` со схемой Bearer/Basic | High, скрыть credential value | Имя поля и схема регистронезависимы; сам секрет сохраняет регистр до замены. Захватить значение до текстовой границы полностью. Не считать `WWW-Authenticate: Basic realm=…` пользовательским credential. |
| Документированный префикс GitHub и непустой длинный суффикс | High, скрыть кандидат целиком | Префикс проверять с границей слева; не захватывать середину обычного идентификатора. Для `ghs_` использовать рекомендации 2026 года. Для остальных длины/алфавиты, выбранные реализацией, являются эвристикой и должны быть закреплены fixtures. |
| Присваивание чувствительному имени в `.env`/JSON-подобном тексте | High для узкого перечня явных имён, review для более общих | Предлагаемые имена: `password`, `passwd`, `api_key`, `access_token`, `refresh_token`, `client_secret`, `secret_key`, включая согласованные варианты регистра и разделителей. Это эвристика TGSUM, не общий формат credentials платформ. |
| URL `scheme://user:password@host` | High, скрыть userinfo | Искать только внутри authority, с непустой частью после `:`. Сначала определить компоненты, затем при необходимости работать с percent-encoding. `%40` не является разделителем `@`. |
| Самостоятельный JWT/JWE-подобный текст | Medium, показать для review | Три или пять Base64url-сегментов — кандидат. Нельзя объявлять его действительным access token. Внутри явного Authorization применяется правило заголовка. |

Конкретные рекомендации по реализации:

- Метки ключей для первого набора: `PRIVATE KEY`, `ENCRYPTED PRIVATE KEY`,
  `RSA PRIVATE KEY`, `DSA PRIVATE KEY`, `EC PRIVATE KEY`, `OPENSSH PRIVATE KEY`.
  Поиск маркера допустим и внутри процитированного сообщения. Скрытие остатка
  после незакрытого блока намеренно может убрать полезный текст; preview должен
  объяснять объём замены. Это консервативное решение TGSUM для оборванных копий.
- В явном заголовке нет основания вводить минимальную длину пароля или
  Bearer-токена. Пробелы/табуляция вокруг поля допустимы как эвристика обработки
  скопированного текста; перенос строки не должен захватывать следующее поле.
  Локальное декодирование Basic допустимо для уточнения находки, но требование
  корректного UTF-8 исключило бы часть допустимых credentials.
- Для GitHub брать максимальную последовательность символов выбранного
  алфавита без обрезания до 40, 255 или 520 символов. Нижний порог уменьшает
  ложные находки на именах переменных, но может пропустить короткую оборванную
  копию. Утверждения о полноте требуют отдельных оснований для каждого типа.
  Checksum в минимум не нужен: валидатор исторического формата мог бы скрыть
  от пользователя незнакомый новый вариант.
- Для присваиваний фиксировать весь identifier и применять явный перечень
  имён/суффиксов; совпадение `secret` внутри произвольного слова недостаточно.
  Кавычки могут содержать пробелы и escape-последовательности. Нельзя скрыть
  только первый фрагмент значения и оставить хвост. Имена `token` и `key`
  без уточнения дают много ложных находок, поэтому подходят для medium review.
- URL-правило не должно принимать email, пароль в query или `name:pass@host`
  внутри path за userinfo. Username без двоеточия не является находкой этого
  правила. Percent-encoded пароли скрываются как исходный текст; URL не нужно
  открывать. Полностью закодированный разделитель `:` остаётся явным пределом
  минимального правила, если отдельно не реализовано его распознавание.
- Для JWT можно локально декодировать только ограниченный по размеру header
  и проверить JSON-объект с `alg`, чтобы уменьшить ложные находки; это также
  эвристика. Не требовать буквального начала `eyJ` как полной спецификации JWT.
  Пустая подпись JWS и пустые допустимые части JWE требуют отдельных fixtures.
  Проверка подписи, issuer, expiry и сетевой introspection не входят в задачу.

## Локальность, границы и проверка

Следующие требования — выводы для TGSUM из цели задачи:

- Сканировать весь текст, который реально попадёт в bundle, включая названия,
  описания, цитаты и ссылки. Провести сканирование до форматирования и разбиения,
  иначе токен может оказаться по обе стороны границы частей.
- Сохранять UTF-8 и байты вне замен. Объединять пересекающиеся диапазоны,
  отдавая приоритет полному приватному блоку; вложенный GitHub/JWT-кандидат
  не должен оставить часть одного секрета или породить повторную замену.
- Ограничить память размером обрабатываемого поля/сообщения и числа findings.
  Лимит preview не должен прекращать сканирование оставшегося текста. При
  превышении ресурсного лимита явно прервать подготовку либо полностью скрыть
  соответствующее поле; частично проверенный bundle нельзя назвать проверенным.
- Сводки и журналы содержат тип, количество и положение находок, а не исходные
  secrets. Маскированный preview и Export only не нуждаются в вызовах AI,
  проверках действительности токенов или доступе к аккаунтам.
- Синтетические тесты должны покрыть все метки ключей, незакрытый блок, CRLF,
  разные регистры Authorization, короткий credential, длинный `ghs_` с точками,
  соседние и пересекающиеся находки, Unicode вокруг них, кавычки и escape в
  assignment, URL userinfo с percent-encoding и IPv6 host, а также отрицательные
  случаи: public key, certificate, email, обычный URL path/query, имя переменной.
  JWT/JWE tests отдельно проверяют medium review, включая пустые сегменты.

Ложные срабатывания ожидаемы на учебных примерах, фиктивных credentials и
просроченных токенах: scanner не знает их происхождение. Пропуски возможны
для непрефиксных токенов, cookie/session-строк, неизвестных провайдеров,
нестандартных ключей, обфускации, секретов без подписи, изображений,
вложений и значений, разорванных между отдельными исходными сообщениями.
Отсутствие находок не доказывает отсутствие секретов; scanner не обещает
анонимность, полную DLP-проверку или безопасность дальнейшего использования.
