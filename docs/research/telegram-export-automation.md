# Telegram: экспорт и автоматизация клиента

Проверено **2026-09-26**. Исследование документации и исходников; реальный
аккаунт не подключался, UI-автоматизация не прототипировалась.
Исходники tdesktop: `fcdcf9252be2c5b96c9778f0c0e958632a3fb64c` (ветка dev
на момент проверки; это не обещание поведения всех установленных release-сборок).

## Подтверждённые возможности

1. Telegram Desktop позволяет экспортировать отдельный чат через меню чата
   и сохранить JSON/HTML с выбранными медиа. Полный экспорт аккаунта не является
   обязательным исходным действием пользователя.
   [Официальная инструкция](https://telegram.org/blog/export-and-more).
2. В `Launcher::processArguments` есть `-workdir`, `-startintray`, `-autostart`;
   команды экспорта в разобранной таблице аргументов нет. В просмотренных
   обработчиках локальных URL не найден запуск экспорта истории (найден экспорт
   тестовой темы). Это ограниченный отрицательный результат проверки исходников,
   а не доказательство отсутствия любого возможного внутреннего интерфейса.
   [launcher.cpp](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/Telegram/SourceFiles/core/launcher.cpp#L588),
   [local_url_handlers.cpp](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/Telegram/SourceFiles/core/local_url_handlers.cpp).
3. Exporter использует `account.initTakeoutSession`, `invokeWithTakeout`
   и запросы истории. Копирование его кода в отдельный процесс всё равно
   предполагает пользовательскую авторизацию и сетевое получение истории.
   Это не готовая выгрузка всей переписки из локального cache.
   [export_api_wrap.cpp](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/Telegram/SourceFiles/export/export_api_wrap.cpp),
   [Takeout API](https://core.telegram.org/api/takeout).
4. API может вернуть `TAKEOUT_INIT_DELAY_%d`: экспорт отложен на указанное
   число секунд, остальные устройства получают уведомление. Планировщик обязан
   уважать ожидание и переходить в понятное состояние, а не повторять входы.
   [account.initTakeoutSession](https://core.telegram.org/method/account.initTakeoutSession).
5. Одиночный экспорт имеет корневой объект чата с `messages`; полный — оболочку
   `chats.list`. В TGSUM `core/src/stream.rs` сейчас обрабатывает только вторую
   форму, пропуская остальные ключи. Валидный одиночный JSON может дать пустой
   индекс без ошибки. Это отдельная совместимость, которую нужно реализовать.
   [JsonWriter::start / writeDialogStart](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/Telegram/SourceFiles/export/output/export_output_json.cpp),
   [текущий parser](../../core/src/stream.rs).
6. `result.json` создаётся до окончания экспорта; writer дописывает структуру,
   затем controller завершает Takeout и выставляет `FinishedState`. Одно событие
   создания файла или пауза в его росте не доказывают завершение всех вложений.
   [JsonWriter](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/Telegram/SourceFiles/export/output/export_output_json.cpp),
   [ControllerObject::exportNext](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/Telegram/SourceFiles/export/export_controller.cpp#L404).

## Доступ и условия использования

Telegram требует собственный `api_id` для распространяемого приложения;
предупреждает о дополнительном наблюдении за аккаунтами сторонних API-клиентов
и санкциях за злоупотребления. Выбранный `peer` ограничивает конкретный запрос,
но не превращает пользовательскую сессию в credential только для этого чата.
[Создание приложения](https://core.telegram.org/api/obtaining_api_id),
[API Terms](https://core.telegram.org/api/terms).

API Terms §1.5 содержат широкое ограничение AI/ML, включая deployment.
Content Licensing Terms распространяют ограничения на данные платформы и
описывают возможность исключений при индивидуальном явном, информированном,
продолжающемся согласии всех relevant users в конкретном контексте. Наличие
архива, бота, локальной модели или пользовательской галочки само по себе не
доказывает выполнение этих условий. Точный сценарий требует отдельного решения.
[API Terms](https://core.telegram.org/api/terms),
[Content Licensing Terms](https://telegram.org/tos/content-licensing).

Следствие для продукта: file import сохраняем как механизм локальной обработки;
автоматический `Telegram → AI` не объявляем разрешённым по умолчанию. VM,
официальный бинарник и sanitizer не устраняют вопрос дальнейшего использования.
Не найдено основания утверждать, что любая пользовательская UI-автоматизация
экспорта сама по себе категорически запрещена; также не найдено разрешение,
которое автоматически покрывает предлагаемый фоновый AI gateway.

## Варианты автовыгрузки

| Вариант | Что автоматизирует | Решение |
| --- | --- | --- |
| Watch готового архива | Повторный импорт после действия пользователя | Ближайшая реализация |
| Помощник экспорта | Открытие клиента/инструкция, затем пользователь запускает экспорт | Кандидат на основной UX; deep link проверить на версии клиента |
| Неизменённый Desktop в отдельной VM/desktop session | Управление меню экспорта через UI | Ограниченный feasibility spike |
| Форк tdesktop с IPC-командой к exporter | Управляемый запуск и точное событие завершения | Отложить: стоимость собственного клиента |
| TDLib/MTProto/Takeout | Прямое получение истории по API | Research, до отдельного решения по доступу и AI-policy |

### Если под «фоновым клоном» имеется в виду VM

Техническая гипотеза: официальный бинарник в отдельной локальной VM, отдельный
профиль, самостоятельный вход пользователя через UI, сохраняемая сессия внутри
VM; helper видит интерфейс, TGSUM получает только папку завершённого экспорта.
Это изолирует доступ helper к основной рабочей среде. Сессия Telegram внутри
VM по-прежнему имеет доступ к аккаунту; VM сама по себе не ограничивает её тремя
чатами. Один `-workdir` разделяет профиль, но не создаёт границу безопасности ОС.

Фоновое окно также не равно headless: Qt-приложению нужны графическая сессия,
диалоги и обработка блокировок/подтверждений. Контейнер, виртуальный display,
VM и отдельная desktop session — разные варианты, их надёжность не измерена.

**Минимальный spike:** одна ОС (сначала Linux), одна зафиксированная release-версия
и один тестовый чат с предоставленными для эксперимента данными. Helper —
детерминированная машина состояний с accessibility selectors, если они доступны.
Автономному LLM не выдаём доступ к авторизованному клиенту.

```text
needs_login → ready → user_requested → exporting → validating → published
                               ↘ waiting_for_platform / needs_attention / failed
```

Критерии перехода к экспериментальному выпуску:

- Пользователь сам входит; существующий `tdata` не копируется. На экране видны
  подключённый аккаунт, выбранный чат и журнал запусков. Есть Stop и Disconnect.
- Экспорт подтверждён для нужного account/chat ID, а не только совпавшего имени.
  Неоднозначность, другое окно, новый dialog или смена версии останавливают helper.
- Повторные запуски на тестовом наборе, отмена, сетевой разрыв, ожидание платформы,
  disk full, блокировка сеанса и перезапуск не приводят к импорту чужого/неполного scope.
- Helper сначала ждёт UI completion, затем валидирует JSON и доступность
  разрешённых вложений; публикует собственный manifest с hash и завершённым run ID.
- Экспорт пишется в отдельный staging-каталог; разрешённые файлы копируются в
  новый snapshot. Архив и файлы сессии никогда не попадают в context bundle.
- При недоступной accessibility автоматизация по координатам не получает статус
  поддерживаемой без отдельной оценки. Результат spike — go/no-go с логами,
  а не обещание будущего кроссплатформенного cron.
- Перед подключением реальных рабочих чатов закрывается policy review для
  acquisition и отдельно для retention/AI. Обход ограничений платформы исключён.

### Если имеется в виду модифицированный официальный клиент

Можно проектировать вызов внутреннего exporter через локальный IPC и получать
`FinishedState`. Но такой бинарник уже является нашим производным клиентом.
Он требует сборок, обновлений безопасности, проверки лицензирования, собственных
API credentials и поддержки авторизации. Telegram публикует код под GPLv3;
его документация отдельно требует публикации кода при использовании исходников.
Лицензионную границу с MIT core нужно определить до заимствования кода.
[LICENSE](https://github.com/telegramdesktop/tdesktop/blob/fcdcf9252be2c5b96c9778f0c0e958632a3fb64c/LICENSE),
[требования к приложениям](https://core.telegram.org/api/obtaining_api_id).

## Практический выбор

Сначала одиночный JSON → явный snapshot → watcher → diff → ручной запуск анализа.
Параллельно допустим исследовательский helper над неизменённым клиентом.
Встраивать или распространять форк Telegram ради scheduled export сейчас
не оправдывается подтверждённой пользой и стоимостью поддержки.
