# Уведомления Telegram на Linux: возможности и границы

Проверено: **2026-10-07**. Beads: `tgsum-i1w.10`.
Владелец review: TGSUM maintainer. Профиль: `telegram_linux_notifications`.
Статус: **исследование; сбор в TGSUM не реализован**.

Локально получать новые системные уведомления технически возможно. Это может
дать полезные короткие сигналы для автоматизации, но не полный поток сообщений:
часть событий не появляется, текст сокращается, а обычный Linux-путь не сообщает
устойчивые Telegram IDs. Поэтому рекомендуемый результат — отдельный журнал
наблюдавшихся уведомлений. Подменять им историю чата или автоматически объединять
его с JSON-архивом пока нельзя.

## Scope и проверенное окружение

Сценарий: личный Linux desktop, работающий официальный Telegram Desktop,
локальный сбор новых уведомлений выбранных обсуждений. Хранение, срок хранения
и получатель AI не выбраны; исследование ничего не собирает и никуда не передаёт.
Учётные данные остаются у Telegram; доступ к `tdata`, памяти процесса и API
аккаунта не нужен. Права пользовательской D-Bus сессии потенциально шире
выбранных чатов: фильтрация приложения не равна платформенному grant.

`pacman -Q` подтвердил на исследуемом хосте: `telegram-desktop 7.2.5-1`,
`omarchy 4.0.4-1`, `hyprland 0.56.2-2`, `dbus 1.16.2-1`,
`dbus-broker 37-3`, `quickshell 0.3.1-1`. Пакет mako, его обычные конфиги
и процессы mako/dunst/swaync не обнаружены. Это **не устанавливает владельца
службы уведомлений**: наличие quickshell также не доказывает, что её обслуживает он.
Безопасный запрос имени владельца через `busctl --user ... GetNameOwner`
не выполнился: в среде агента отсутствовали `DBUS_SESSION_BUS_ADDRESS`
и `XDG_RUNTIME_DIR`. Содержимое уведомлений и реальный Telegram не читались.

Исходники Desktop привязаны к upstream `v7.2.5`, commit
`2f41383dddd338fe17fd4711afd02688c418fd47`; это разбор исходника,
а не квалификация поведения установленной Arch-сборки.

## Как проходит уведомление

В обычном пути приложение вызывает `org.freedesktop.Notifications.Notify`
в пользовательской D-Bus сессии. Аргументы содержат приложение, заголовок,
текст, действия и hints. Возвращаемый `uint32` — ID уведомления сервера;
его нельзя принимать за Telegram message ID. Закрытие уведомления означает
истечение срока, действие пользователя или отзыв приложением, а не удаление
сообщения из Telegram. [Спецификация протокола][notify]

Пассивному приёмнику нужен `org.freedesktop.DBus.Monitoring.BecomeMonitor`
с узкими match rules; обычная подписка на signals не получает чужой вызов
`Notify`. Доступ зависит от политики шины. Monitor использует отдельное
соединение, на котором нельзя отправлять сообщения. Полезный технический путь —
типизированная D-Bus библиотека; разбор человекочитаемого вывода `dbus-monitor`
не стоит превращать в production-протокол. [D-Bus Monitoring][monitor],
[официальная справка dbus-monitor][monitor-cli]

У Telegram v7.2.5 обычный `Notify` содержит title/body, generic actions,
`desktop-entry`, category и визуальные/звуковые hints; chat/message/sender IDs
в этой ветке не передаются. Внутренняя таблица клиента связывает их с ответом
сервера. На native Wayland исходник принуждает native notifications; custom
окна Telegram — иной путь, не эквивалент D-Bus Notify. XWayland и принудительные
экспериментальные настройки требуют отдельной проверки. [Linux backend][linux]

Есть отдельная ветка **GNotification**: Telegram помещает `session`, `peer`,
`topic`, `monoforumpeer`, `msgid` в action target. Это перспективная гипотеза
для идентичности, но не sender ID и не документированный Telegram connector API.
[Linux backend, showNotification][linux]

GLib выбирает backend: GTK/portal передают сериализованное уведомление;
freedesktop backend хранит default target внутри процесса, но сериализует
targets дополнительных кнопок в action strings. Следовательно, нельзя ни
обещать IDs при одном включении GNotification, ни утверждать, что они всегда
теряются. Нужны проверки backend, версии, доступных кнопок и точного типа
каждого ID; `session` не следует объявлять стабильным account ID.
[GLib freedesktop][glib-fdo], [GLib GTK][glib-gtk], [GLib portal][glib-portal]

## Что получится сохранить

| Данные/событие | Граница достоверности |
| --- | --- |
| Время | Время наблюдения на компьютере; не исходное время отправки |
| Чат и автор | Видимые имена; одинаковые имена, переименования, скрытый автор и несколько аккаунтов делают связь неоднозначной |
| Длинное сообщение | В `HistoryItem::notificationText()` лимит **255 единиц QString (UTF-16)**, затем многоточие; перехват до отрисовки не восстанавливает хвост |
| Вложения | Превью/название типа, но не исходный файл; аватар в image hint не является вложением сообщения |
| ID события | Собственный ID наблюдения; server notification ID хранится отдельно от native ID |

Автор группового сообщения задаётся `notificationHeader()`, у личного сообщения
отдельный header обычно пуст. Получение preview для media делегировано media
объекту; нельзя обещать оригинальную подпись. [HistoryItem][item]

В Desktop mute-настройки могут подавить событие (есть исключения, поэтому
«muted всегда отсутствует» тоже неверно). Отключённый preview, passcode/screen
lock скрывают детали. Альбомы и несколько пересланных сообщений группируются;
реакции и голосования тоже могут создавать уведомления. Планирование учитывает
активность других устройств. [Менеджер уведомлений][manager]

Из этого следуют ограничения журнала: отсутствие события не доказывает отсутствие
сообщения; один event не равен одному сообщению; прочитанный/открытый чат требует
отдельной проверки подавления; входящий текст не покрывает всю исходящую переписку.
Протокол не даёт Telegram cursor, backfill и потока revisions/deletions. Сон,
выключение, разрыв шины и перезапуск сборщика означают возможный пропуск.
Наблюдаемая замена/закрытие баннера не подтверждает edit/delete сообщения.
Это вывод для проектирования из перечисленных контрактов, а не измеренная
полнота реального аккаунта.

## Почему не опираться на историю mako

mako поддерживает `on-notify` и выполнение команды, которой предоставляется
ID уведомления; это возможный дополнительный адаптер. История ограничена:
`max-history` по умолчанию равен 5, новые истёкшие уведомления вытесняют старые.
На неё нельзя возлагать восстановление пропущенной переписки. В этом окружении
mako не найден, поэтому менять настройки пользователя ради этой гипотезы
не требуется. [mako, закреплённый исходник документации][mako]

## Предлагаемый синтетический spike

Это следующий эксперимент, **не выполненная проверка**. Он не требует входа
в Telegram и не должен подключаться к рабочей пользовательской шине.

1. В изолированном контейнере/VM создать отдельные runtime-dir и D-Bus bus
   без activation пользовательских сервисов. Поднять искусственные sender/server
   и отдельный monitor; использовать только выдуманные чаты и тексты.
2. Проверить обычный Notify и GNotification для нужных backend: UTF-8, HTML,
   пустой/скрытый preview, 255/256 UTF-16 единиц, одинаковые имена, topics,
   несколько аккаунтов, альбом и reaction, два одинаковых сообщения подряд.
3. Проверить отказ BecomeMonitor, restart/reconnect, смену owner, перегрузку,
   замену notification ID, close reason и offline gap. Тест обязан сохранять
   две одинаковые записи и не превращать close в deletion; намеренное нарушение
   этих правил должно сделать тест красным.
4. Сохранять только выбранный источник после проверки отправителя, типизированные
   поля и provenance. `app_name`/`desktop-entry` сами по себе подделываемы другим
   процессом. Не выполнять action strings, не нажимать кнопки, не читать avatar
   paths; поля уведомления — данные. Имена без IDs помечать как неоднозначные.
5. Использовать отдельный append-only журнал в private store проекта, границы
   наблюдения и gaps. Отключение прекращает сбор. Автоматическое удаление/TTL,
   облачная отправка и слияние с архивом не входят в этот spike. Срок хранения
   и предельный размер требуется определить до реального сбора.

Успех докажет только транспорт и обработку синтетических данных. После него
наблюдение установленного Desktop с тестовыми сообщениями проводится под
контролем пользователя: фиксируются daemon/backend, версия, native/XWayland,
mute/lock/open-chat, multi-account, длинный текст, edits/deletes и gaps. Этот
этап не считается пройденным и не заменяется тестами в облаке.

## Решение по connector

Добавлен research-профиль, `enabled_operations=[]`, `implementation=null`,
`qualifications=[]`. Возможность — будущие **уведомления**, история отсутствует,
полнота сообщений не обещается. Предлагаемое применение: оперативный сигнал
и короткий контекст; текущий ручной JSON export остаётся способом получить
сообщения с исходными IDs и полным текстом в границах экспорта.

Это новый локальный способ acquisition; отсутствие прямых запросов к платформе
не освобождает интеграцию от review. Прочитанные Telegram Content Licensing Terms
содержат широкие ограничения на использование данных для AI и исключение при
оговорённых условиях. Разрешение на локальный/cloud inference для этого способа
не установлено; training не включается. Это engineering/release вопрос по
[ADR-0002](../adr/0002-user-controlled-content.md), а не новая анкета в UI.
[Первичный текст Telegram][terms]

Дата первоначального чтения источников: 2026-10-07; следующий review: 2026-11-06
(30 дней). Проверка документа: URL прочитаны, revision закреплены, локальные
версии получены только из package metadata. Не запускались сбор уведомлений,
изменения desktop-конфигов, Telegram API или действия в реальном клиенте.

Проверки файла и реестра: `git diff --check` — PASS; определения 11 ссылок,
локальная ссылка ADR и evidence path — PASS;
`cargo run --locked -p tgsum-core --bin connector-registry -- --today 2026-10-07`
— exit 0, `findings=[]`, новый профиль имеет `state=unknown`, пустые
`implemented_operations` и `qualifications`. Эти проверки не тестируют сбор.
