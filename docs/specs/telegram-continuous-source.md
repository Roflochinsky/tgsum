# Постоянный локальный источник Telegram

Дата: 2026-10-08. Beads: `tgsum-i1w.13`. Это контракт реализации;
готовность определяется проверкой установленного приложения, а не этим документом.

## Результат для пользователя

TGSUM получает текстовые наблюдения выбранного чата из диагностических логов
штатного Telegram Desktop 7.2.5 на Arch Linux. Пользователь уже вошёл в Desktop;
нового API-входа, бота и изменения клиента нет. Один подтверждённый аккаунт.
Чат и сообщения связываются по native IDs, имя используется только как подпись.
Предоставленный JSON остаётся начальной историей и источником медиа.

Запуск/остановка и состояние источника доступны в проекте. Новые наблюдения
сохраняются локально и применяются к snapshot; подготовка локального пакета
использует актуальный snapshot. После перезапуска сбор продолжается с сохранённой
позиции. Фоновый запуск в пользовательской графической сессии позволяет закрыть
окно TGSUM. Stop отключает сбор и восстанавливает управляемый режим Desktop.
Новая внешняя публикация и автоматический AI Run в эту задачу не входят.

## Проверка источника до реализации

[Review диагностических логов](../research/telegram-debug-logs-2026-10-08.md)
закрепляет Desktop commit и layer 229, activation/rollback, формат и ограничения.
Первичные источники перечитаны 2026-10-08. Платформенные AI/content вопросы
остаются открытыми; этот локальный источник не добавляет AI-handoff. При постоянном
режиме source scope по-прежнему глобален: Telegram пишет логи других чатов
до фильтра TGSUM. Собственный журнал сохраняет только выбранный typed peer.
Исходные логи не копируются в пакет, не публикуются и не удаляются сборщиком.
Session DB, cookies, tdata contents и память процесса не читаются.

Registry остаётся `research`, без enabled operations и production qualification
до завершения независимой проверки и реального непрерывного потока.

## Хранение и применение

Ограниченный журнал spike заменяется отдельным append-only журналом наблюдений
в embedded redb **2.6.3**. Это закреплённая версия, не заявление о новейшей.
[Cargo.toml](https://github.com/cberner/redb/blob/v2.6.3/Cargo.toml) задаёт MSRV 1.85
(ниже workspace 1.88).
[Builder](https://github.com/cberner/redb/blob/v2.6.3/src/db.rs) принимает открытый
`std::fs::File`; [transaction](https://github.com/cberner/redb/blob/v2.6.3/src/transactions.rs)
обеспечивает atomic commit с `Durability::Immediate`. Источники прочитаны
2026-10-08. Cache задаётся явно; default cache 1 GiB не используется.

* Создание только в новой приватной директории; существующий чужой каталог,
  пустая чужая DB или несовпадающая привязка отклоняются до открытия для записи.
* Путь открывается по компонентам без symlinks. Журнал записывается через
  удерживаемый file handle; замена пути не перенаправляет запись в чужой файл.
  Приватный marker связывает scope и inode DB до recovery/open. Блокировка
  запрещает второго writer. Подмена marker/директории проверяется перед записью.
* Events, dedup index, latest-message index, tombstones, counters и позиции
  исходных файлов фиксируются одной транзакцией. Нет общего лимита 10 000 событий,
  перечитывания всех событий при poll, автоматического TTL или очистки истории.
* Буферы приложения ограничивают размер poll/packet и страницы чтения;
  cache фиксирован. Metadata allocator redb растёт с размером DB, поэтому
  постоянный общий RSS независимо от размера истории не обещается.
  Disk растёт с историей. При ошибке commit результат может быть неизвестен:
  session останавливается до reopen/recovery атомарного состояния. После
  перезапуска незафиксированный poll повторяется.
* Сохраняются все уникальные наблюдения. Более старый history packet не отменяет
  новый edit; observed channel delete оставляет tombstone, включая delete до
  появления сообщения. Неопределённый non-channel delete остаётся gap.
* Project apply читает ограниченную страницу событий и сохраняет native IDs,
  bootstrap-сообщения, темы, ответы и attachments. Публикация immutable snapshot
  и Project CAS идемпотентна; checkpoint подтверждается после публикации.
  Replay после crash не создаёт дубликатов и не откатывает новый snapshot.

Реализованные storage/Project/package/worker/UI и точная граница проверок описаны в
[developer runbook](../development/telegram-continuous-source.md). Успешный
commit и это описание не заменяют управление клиентом, background, установку
и реальную проверку нового сообщения.

## Честная полнота и жизненный цикл

Transport dump предшествует application acceptance. Это наблюдения, не полная
история и не гарантированный event feed. Restart, truncation, rotation,
unsupported packets и offline interval видны в статусе. Отсутствие замеченного
gap не доказывает отсутствие потерь. Имена отправителей берутся только из
известного соответствия ID; неизвестный отправитель показывается по ID.

Включение runtime debug требует штатного quit/relaunch: второе `-debug` не
включает его в работающем экземпляре. Управление сохраняет исходный запуск и
различает debug, включённый пользователем, и debug, включённый TGSUM. Новые
desktop/systemd настройки создаются с backup и документированным rollback.

## Проверка результата

Синтетические regression tests: больше 10 000 событий; точные большие IDs/UTF-8;
selected peer filtering; дубликаты; late edit/delete; partial record; rotation,
truncation и restart; transaction failure/crash; восстановление checkpoint;
чужой output, подмена файла/каталога и concurrent writer. Project apply сохраняет
bootstrap/media, выдерживает CAS conflict и повтор. UI проверяется в запущенном
Tauri, затем в установленном background режиме с перезапуском.

Реальное новое сообщение проверяется при пользовательском управлении чатом;
реальные edit/delete квалифицируются отдельно. Fixtures не заменяют это доказательство.
Финал требует full workspace gate, независимого verifier и GitHub Actions на
точном SHA, включая Arch. Полная автоматизация не считается готовой по одному
хранилищу или по зелёному CI.
